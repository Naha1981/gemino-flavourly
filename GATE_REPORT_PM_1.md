## 1. What was built

**PulseMap for Campaigns** — the pre-launch intelligence layer inside Marketing → Campaigns:

```
Draft Campaign → Simulate Reactions → Improve Message → Launch (unchanged route) → Measure (PM-2 hook)
```

### New service (`apps/main/lib/pulsemap/`)
| File | Role |
|---|---|
| `types.ts` | Shared types + the PII contract (aggregate-only AI surface) + the disclaimer/unavailable constants |
| `aggregate.ts` | `summarizeSegments` (per-segment counts/averages — framework-free) + `detectPII` tripwire (SA phone/email patterns, separator-normalized) |
| `demo-forecast.ts` | The DETERMINISTIC Demo-Mode forecast: explainable rubric over the owner's draft + seeded segment summaries; honestly labelled (confidence `low`, "DEMO FORECAST", "does not promise customer behaviour") |
| `prompt.ts` | The LLM prompt builder — grounded in segment counts/averages, own past campaigns, public review themes (lexicon words only), public market signals; system prompt forbids guaranteeing behaviour |
| `ai.ts` | The approved provider chain (Groq `openai/gpt-oss-20b` → Gemini fallback, same as the app's responder) + `validateForecast` (hard-fail on missing score/segments/copy; clamp 0-100; derive soft fields) |
| `engine.ts` | Orchestration + `hashSimulationInput` (sha256 cache key) + the honest failure contract |
| `store.ts` | Drizzle store — **tenant-scoped by construction** (every read/write keys on `tenant_id`); demo scope via the UI-3R `liveRowsOnly` rule |

### New API (all tenant-isolated; none can send)
- `POST /api/marketing/pulsemap/simulate` — builds the anonymized context, guards (master kill switch + `aiEnabled`/`manualMode`), cache-check, runs the forecast, persists ONLY `campaign_simulations` rows. **Zero jobs/messages/outbox writes.**
- `POST /api/marketing/pulsemap/[id]/apply` — copies the improved copy onto the DRAFT campaign + stamps `applied_at`. Foreign tenant ids → 404.
- `PATCH /api/marketing/campaigns/[id]` — edit a draft (the "improve the message" step).

### New UI (`/dashboard/marketing/campaigns`)
- **Campaign Builder** (client): draft form → *Save draft* → **Simulate customer reaction** → results → *Use improved version* / *Keep my original* → *Launch campaign* (existing launch route, untouched).
- **PulseMap panel**: campaign score 0-100, readiness badge (Ready/Improve/Rework), per-segment reaction matrix with intent + best-fit chip, predicted objections, likely WhatsApp replies, risk flags, suggested improved copy + why, confidence + assumptions, demo/AI source chip, cached-note.
- **The disclaimer is structural**: rendered on the SSR page, in the panel's result state, unavailable state, and loading state, and returned by both API routes (`Forecast only. Real results are measured after launch.`).
- Existing-draft quick-load chips + PulseMap score chips on the campaign list.

### Schema (additive only; mirrored in both migration paths)
`drizzle/0023_pulsemap_simulations.sql` + `lib/db/schema.ts` + `lib/db/migrate-ddl.ts` (section 28; idempotent `CREATE TABLE IF NOT EXISTS`):
- `campaign_simulations` — the forecast + the anonymized `segment_summaries` audit trail (no PII columns)
- `campaign_simulation_segments` — the reaction matrix rows
- `campaign_simulation_feedback` — **PM-2 hook**: predicted vs actual replies/bookings/recovered cents

Demo seed: 2 seeded simulations (The Grand Bistro campaigns, generated by the same deterministic forecaster), wiped with the deadbeef set.

### Demo Mode behaviour (the owner's screenshot workflow)
Demo Mode ON → the simulate button runs the **deterministic demo forecaster** over the deadbeef sample data: no external AI call, no AI budget spent, works offline, clearly labelled. Live mode → the real Groq/Gemini chain; ANY failure → `status: 'unavailable'`, reason, no scores, nothing persisted.

## 2. What was NOT built (by design)

- **No sends**: the launch route, jobs/outbox, operator, webhooks, billing, auth/middleware are untouched (`git diff` proves the launch route has zero changes).
- **No after-launch measurement yet**: `campaign_simulation_feedback` is structure-only — filling actuals (replies/bookings/recovered rand per launched campaign) is PM-2.
- **No DeepPersona / CustomerSim / Parastore**: treated as research inputs only; nothing was installed or imported. The behavioural model is Flavourly's own rubric + the approved provider chain.
- **No segment-to-campaign reply attribution** — PM-2.
- Live-mode simulations are never persisted when unavailable (no clutter rows, no fake history).

## 7. Risks

- **LLM forecast quality** is provider-dependent; validation enforces shape/sanity but a poor model still produces poor words. Mitigations: strict JSON contract, score clamping, honest confidence + assumptions shown to the owner, deterministic demo path for marketing.
- **Cache key granularity**: hash covers draft + segment counts + signal counts; identical inputs reuse the stored forecast (intended). Editing the message invalidates it.
- **Demo forecast is a rubric, not a model** — deliberately labelled low-confidence and "not a live AI prediction"; no one can mistake it for a real forecast.
- **New tables add wipe-surface**: demo simulation rows are deadbeef-prefixed and wiped with the demo set; real simulations are never wiped.
- **`?tenant=` create/launch caveat**: the builder propagates `?tenant=` to simulate/apply/PATCH (resolver routes). POST-create and the launch route remain own-tenant (launch = send path = untouched by mandate). Super admins creating brand-new campaigns inside a viewed tenant is not supported in PM-1.
